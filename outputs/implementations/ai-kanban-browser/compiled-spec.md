# AI Kanban — Browser Workspace for Human-AI Work

## 1. Architecture and Board Workspace lifecycle

Build a polished, implementation-ready static JavaScript application for GitHub Pages. AI Kanban is a calm, local, folder-backed Kanban workspace for human–AI collaboration; it has no backend, server routes, server actions, serverless functions, sockets, or separately installed local service. Cards are durable workspaces for plans, execution, research, outputs, and collaboration. The useful core works without any configured AI provider.

Use semantic HTML, modern CSS, and standards-based ES modules. Prefer browser APIs over frameworks; a small build step is allowed only when deployable assets and deterministic dependency versions are checked in. The deployable root contains `index.html`, all URLs are relative so the app works below a GitHub Pages repository subpath, and all required JavaScript and WebAssembly are vendored rather than loaded from a mutable CDN. Put CPU-heavy SQLite, parsing, search, and transformation work in Web Workers. Keep all domain state behind typed repository/service interfaces; UI modules never issue raw storage queries. Validate imported files and external responses before domain state accepts them.

A Board Workspace folder is the portability, local trust, collaboration, and persistence boundary. It contains `board.sqlite`, a versioned manifest, relative attachments and artifacts, exports, root agent instructions, and private coordination records. The manifest identifies the workspace, format/protocol versions, workspace ID, primary state file, reserved directories, application-owned files, generated bootstrap paths and fingerprints, and schema version. Resolve every application path against the selected root; reject empty, absolute, `..`-traversal, symlink-escape, or outside-root paths. Never modify or delete unrecognized files. Treat every workspace file, attachment, imported packet, card, and generated output as untrusted data; render safely and never execute it merely because it is in the folder.

First run prominently offers **Open Board Workspace**, **Create Board Workspace**, and **Try demo**. Directory selection uses `showDirectoryPicker()` only from an explicit user gesture in a secure context, then requests read/write permission. Try demo visibly offers **Create a real demo workspace**, which follows normal folder checks, installs agent bootstrap files, and seeds the Personal Research board for immediate local-agent use, or **Try in memory**, which creates no folder, disables local-agent integration, and requires export to retain changes. On unsupported browsers, explain that only the in-memory/import-download path is available. Open, create, demo, reconnect, import, and activation are single-flight: disable competing entry actions until the picker or activation completes.

Persist `FileSystemDirectoryHandle` only in IndexedDB for recent-workspace reconnection. On return, query permission and request it again only from a user gesture. Show folder name, permission mode, active read-only/writable state, dirty/saving/saved/conflict status, and last successful durable write; never imply durability without a writable handle. Before Open, Create, Try demo, reconnect, Close workspace, or replacement of dirty state, require successful save or confirmation; cancellation changes nothing. Close clears in-memory domain state. Offer explicit portable archive export. Feature-detect File System Access API; unsupported browsers use honestly labeled workspace archive import/export, not connected autosave. Give specific recovery guidance for revoked permission, missing files, corrupt state, invalid manifest, unsupported future workspace version, partial export, and unsupported browser.

Connected Chromium workspaces autosave through a serialized save queue. Browser preferences, permissions, and performance caches may use browser storage, but the selected `board.sqlite` is canonical. Coalesce rapid edits without losing the final edit. Before replacing a file, compare its current revision and content fingerprint with the last-read signature; unexpected external change aborts saving, reloads or opens explicit conflict recovery, and never silently overwrites. Retain prior bytes until replacement closes successfully. Failed or cancelled writes remain dirty and recoverable. Coordinate tabs with Web Locks where available plus `BroadcastChannel`; only one tab writes a workspace, and a second tab is read-only unless it acquires the workspace lock.

The first-run sample is the same Personal Research board on both paths, with cards for a macroeconomic pulse, activities with a four-year-old in São Paulo, family trips, a collaborative vacation planner, and other age-appropriate activities. The recurring-research workflow records each monitoring cycle’s run date, cadence, lookback window, exact topic, news/events mode, new findings, retained decision-relevant context, source coverage, and gaps. Before a cycle, read durable topic memory and prior reports. Memory records stable fingerprint, normalized subject, concise claim, source URL/publisher, evidence date, first/last seen cycles, content hash, relevance, and `current`, `updated`, `superseded`, `dismissed`, or `uncertain` state. Maintain a source and coverage ledger; classify findings as new, materially updated, unchanged context, duplicate, corrected, or no longer current; preserve source-backed lineage; and allow inspection, search, correction, dismissal, pinning, export, and explicit forgetting without changing immutable historical reports.

## 2. SQLite schema and repository operations

Run pinned, locally hosted SQLite WASM in a dedicated Worker. The Worker owns the sole live SQLite connection and exposes a validated message-based repository API for create, open, snapshot/query, mutation, export, close, and health. The worker imports an existing database from `Uint8Array` and exports complete database bytes. The external `board.sqlite` is canonical; in-memory SQLite, OPFS, IndexedDB, and caches are working state only. Document a practical workspace-size limit because saves serialize and rewrite the complete database; keep export and UI responsive.

Enable foreign keys, rollback-journal mode, full synchronous durability, bounded busy timeout, explicit transactions, deterministic transactional migrations, and a metadata table carrying schema version, workspace revision, and control state. Reject unsupported future schemas while preserving original bytes before migration. Use stable text IDs, UTC ISO 8601 timestamps with timezone offsets, integer ordering keys, and indexes for board/column ordering, full-text or normalized search, active turns, activity event chronology, dependencies, memory fingerprints, output history, and coordination lookups. Use integer smallest units for any monetary value. Keep append-only activity/events separate from current snapshots. Validate all worker messages and SQL parameters; never concatenate user content into SQL. Surface migration, corruption, lock, busy, conflict, validation, and export errors as typed results with actionable recovery.

Persist at least these entities and constrained lifecycles:

- `workspaces`, `boards`, and ordered `columns`. The default column IDs and display order are Inbox, Planning, In Progress, Review, Blocked, and Done; custom layouts retain stable IDs, names, order, and optional descriptions.
- `cards`: stable ID; board/column IDs; integer position; `task`, `question`, or `result` kind; title; Markdown description; priority `P0`–`P3`; assignee; human/AI attention state; created/updated/seen/archived timestamps; dependencies; relative artifact paths; provenance; last-change actor; current-turn and latest-output projections; and archived state. Define valid creation, editing, movement, reordering, archival, restoration, and deletion rules. No generic card field substitutes for concrete domain fields.
- `plan_items`: stable IDs, card/turn ownership, ordered checklist entries, explicit state, actor, timestamps, and dependencies.
- `execution_turns`: stable ID, card ID, monotonic display number, `queued`, `claimed`, `running`, `needs_input`, `review`, `complete`, `failed`, or `cancelled` status; trigger/requester; assigned actor and run ID; idempotency key; instruction and item-revision snapshot; queued/claimed/started/updated/completed timestamps; checkpoint/plan state; final summary; typed error details; output IDs; and memory read/write lineage. Completed identities and histories are immutable.
- `decision_threads`, proposals, option comparisons, feedback rounds, questions, answers, selections, commitment gates, and deep-work snapshots. Their phases are `briefing`, `exploring`, `needs_feedback`, `committed`, `deep_work`, `review`, and `accepted`, independently projected into board columns.
- `outputs` and `output_surfaces`: stable IDs, card and turn ownership, type, title, payload or relative payload reference, schema version, `draft`, `streaming`, `complete`, `failed`, `stale`, `superseded`, or `approved` status, source, timestamps, provenance/lineage, optional artifact path, actions, version, and comparison links. Support typed text, status, link, program, table, diff, image/media, file, log/terminal, form, and canvas/diagram renderers.
- `activity_events`: stable ID, semantic type, actor, target, actor-authoritative UTC timestamp, short summary, structured payload, visibility, and correlation/trace ID. Events are append-only; redaction preserves explanatory audit metadata and never logs secrets or unnecessary raw internals.
- `research_memory`, report cycles, source coverage, and durable topic-memory lineage as described above.
- control, agent, grant, mailbox/outbox, heartbeat, idempotency, and bootstrap integrity records required by the coordination protocol.

Every mutation returns an updated snapshot or precise change record and marks the external database dirty. Moving/reordering a card and inserting its movement event occur in one SQLite transaction. Completing or failing a turn updates its card projection and workflow position with its final activity event in one transaction. Claim one ready turn atomically with expected revision and idempotency checks; allow at most one active turn per card by default. Explicit Save flushes pending committed mutations through the save queue. A second tab never silently falls back from a connected database to unrelated OPFS storage.

## 3. Human-agent coordination and skill protocol

Install application-owned, versioned agent bootstrap on every created workspace: root `AGENTS.md`, `CLAUDE.md`, and one canonical `.agents/skills/ai-kanban/` bundle containing `SKILL.md`, a dependency-free Python 3 CLI, and thin POSIX-shell and PowerShell launchers. Root instructions point to the canonical skill rather than duplicating its operating contract. Record protocol version, generated paths, and content fingerprints in the manifest. On reopen, validate the whole bundle and offer Repair or Update when absent, outdated, or inconsistent. Never silently overwrite a user-created or user-edited root instruction, skill, or launcher: show a comparison and require confirmation, updating only recognized generated content or explicitly approved managed sections.

The generated instructions require compatible agents started in the workspace to read the manifest and skill, run runtime preflight, register identity and heartbeat, inspect or resume active work, then enter a watch loop without waiting for another conversational nudge. The loop polls with bounded interval and backoff, atomically claims one ready turn, executes validated skill commands, publishes checkpoints, asks for input or completes/yields, and returns to watching while the host session remains alive. An empty queue is quiet, not exit. Stop cleanly on user cancellation, revoked control, workspace closure, unrecoverable integrity failure, or host termination. State plainly that a skill cannot force a terminated host runtime to remain alive, consume later output, or create new model turns; sustained autonomous work needs an explicit host-supported hook, scheduler, or agent runner. Where unavailable, label watch as observation only and provide manual-resume instructions.

Reserve a private coordination directory with a versioned human signal file and a separate versioned state file per approved agent. Each actor is sole writer of its own coordination file; all may read. Every coordination record includes `workspace_id`, protocol version, actor/holder ID, monotonically increasing sequence or control generation, timestamp, requested state, and last observed durable-state revision. Write by safe replacement; ignore incomplete, stale, mismatched-workspace, and lower-generation records. Coordination is only mailbox/commit signaling: durable questions, answers, progress, outputs, and audit history remain in SQLite.

Enforce one acknowledged writer for the primary state file. Control states are `human`, `granting_agent`, `agent`, `reclaim_requested`, and `recovering`; control records carry owner, `holder_id`, `control_generation`, `workspace_revision`, and bounded lease metadata. A generation is an epoch: each mutation verifies generation, holder, and expected revision immediately before writing. Control changes require request and acknowledgment. A requester writes no durable state until the current owner commits or rolls back, closes its writer, publishes final revision, and acknowledges handoff. Human reclaim has priority: the agent completes or rolls back its short transaction, rejects later mutations, publishes `yielded`, and must freshly read and obtain a new grant before resuming. Lease expiry is recovery evidence, never permission to overwrite. Forced recovery invalidates generation, waits for state and journal stabilization, validates integrity, and explains risk before writing. This cooperative protocol does not claim protection from unrelated or malicious software.

Because the browser rewrites whole SQLite files and does not participate in native advisory locks, this control protocol is authoritative. Store generation and workspace revision in SQLite and mailbox records; a grant is valid only if both agree. Before granting, the browser flushes pending saves, increments generation, records the chosen grant in SQLite, closes its writable stream, publishes the signal, and becomes read-only. Freeze the user-confirmed target and, after pending saves, revalidate that exact actor and run before transfer. Before each agent mutation, the CLI reads the latest human signal, opens a fresh SQLite connection, executes `BEGIN IMMEDIATE`, verifies control and revision, applies mutation and audit event, increments revision, commits, closes, then publishes the committed revision. Never hold a transaction during model reasoning, tool execution, artifact generation, waiting, or polling. The browser reloads only after commit marker, journal disappearance, integrity check, and announced-revision verification. Concurrent mutations fail fast with a typed busy result requiring fresh preflight values. Announcement/watch publication failures are typed; an exact post-commit retry with the same idempotency key republishes the durable outbox.

The Python skill uses only `sqlite3`, `argparse`, JSON, and filesystem APIs. It preflights Python and required standard-library modules. If no supported runtime exists, it explains the exact trusted installation command and obtains approval before changes; it never silently installs software or elevates privileges. Expose validated commands for workspace status, ready-work inspection, atomic claim/release, typed mutations, artifact references, structured questions, human answers, yield, heartbeat, grant/regrant, resume, completion, and watch. Mutating commands require expected revision, control generation, actor, run ID, and idempotency key; control revocation and conflicts are explicit failures. Agents use the CLI rather than editing SQLite or mailbox JSON ad hoc.

After create/reopen, show a concise Start your agent step: direct the user to launch Copilot CLI, Claude Code, or another compatible agent in the Board Workspace; use folder name and platform-appropriate guidance rather than fabricating an absolute `cd` path. Show Waiting for agent until a valid workspace-matched heartbeat, then calmly show identity, control state, current turn, and last heartbeat. If several records exist, display the durable SQLite control holder rather than an unrelated newer heartbeat. If heartbeat is missing, provide copyable fallback instructions, bootstrap diagnostics, Repair agent setup, and retry; do not promise all products or versions load generated instructions.

Keep cooperative request/return primary. For a stale controlling agent, offer a copyable guarded recovery command tied to revision/generation only after the user confirms the old process stopped. Preserve partial work by cancelling an interrupted active turn before yielding. Agent turns read prior reports and memory, identify new or materially changed facts, use the baton, and preserve copy/import handoff as fallback.

## 4. Cards, decision loops, execution turns, memory, and output surfaces

The board supports create, edit, duplicate where useful, archive, search, filter, sort, reorder, move, and keyboard/pointer interaction. It shows attention, blocked, overdue/aging, ownership, and useful flow counts without becoming an operations console. Empty boards and columns explain the grouping model and provide creation/filter recovery. Define allowed transitions, visible reasons for prohibited transitions, optimistic-update rollback, persistence conflict handling, and state-aware hooks.

Cards are mixed operational, informational, and navigational workspaces. Compact cards prioritize title, meaningful summary, priority, key attention/status badges, latest result preview, current-turn state, turn count, assignee, and last-change actor. Full detail provides metadata/description editing; plan items; dependencies; turns; decision history; topic memory; activity; provenance; output history; agent questions and human replies; Run again; archive; and publication of polished result cards. Cards remain scannable at rest and open a detail surface without losing selection, scroll, draft input, or active detail state after observed agent commits. Agent-last-changed cards show a calm, accessible violet/teal cue until reviewed, always with icon and text.

Movement and reordering have pointer drag/drop plus complete keyboard movement, visible focus, drag preview, drop targets, cancellation, and rollback. Moving completed work back to Inbox requires **Run again** confirmation and creates a fresh queued turn; it never reopens or mutates the old turn. Initial placement does not automatically execute; expose explicit Ready for agent state. Requeue links prior successful turn, snapshots current instructions, assigns fresh ID/number, and preserves every prior turn. A `needs_input` turn remains active and resumes after answer; cancellation stops later mutation while preserving partial output, activity, and reason.

Implement the vacation decision loop: in Inbox, the human edits destinations and constraints; in Planning, an exploratory turn compares options broadly and receives feedback; only a confirmed move to In Progress with an explicit selected option and **Research selected option deeply** gate completes exploration and queues deep research with dated itineraries; Review presents the latest proposal for revision/acceptance. The initial brief includes goals, suggestions, constraints, preferences, exclusions, budget/effort bounds, criteria, and known unknowns; it is editable until Ready for agent. Exploration presents a bounded structured comparison including criteria fit, evidence, tradeoffs, uncertainty, practical constraints, and differentiation. Missing preferences that can change ranking produce focused questions and `needs_feedback`, not guesses. Humans can rank, shortlist, reject, restore, annotate, add options, and revise constraints; feedback is structured, append-only, and may contain prose. Before each new pass, summarize understood feedback, cite its round, update only affected comparisons, and explain material ranking changes. An agent never infers commitment from positive feedback. Deep-work snapshots selected option, accepted constraints, unresolved questions, evidence, and feedback; it does not silently reconsider rejected options. Changing selection after commitment requires cancellation/replacement and a new recorded gate. Review highlights proposal, assumptions, useful alternatives, evidence dates, unresolved risks, and focused approve/revise actions. Acceptance retains exploration, feedback, superseded proposals, and history.

Outputs are always owned by a turn and versioned. Render Markdown safely for text; syntax-highlighted program artifacts include language, relative file path, copy, and apply only when explicit repository integration exists; tables support schema validation, sorting/filtering/export; diffs support before/after comparison, comments, and approval; images/media support preview, gallery, zoom, download, alt text, and provenance; statuses show metrics/progress/trends; logs/terminals provide streaming distinction, ANSI handling, search, pause, and autoscroll; forms validate submissions; diagrams provide spatial controls and export. Surfaces can be ordered, pinned, minimized, opened, copied, downloaded, commented on, approved, applied, compared, or exported as appropriate. Failed/stale surfaces explain cause and recovery. Applying output externally is explicit and auditable. Feature the latest successful output with preview, age, status, and Open action; retain dated older versions one action away in ordered history and support comparison with new/changed/unchanged/superseded/failed labels.

Provide provider-neutral AI handoff: export a selected card as compact versioned JSON and Markdown packet containing intent, context, plan, relevant activity, requested response shape, and provenance; copy/download it for any assistant; import response packet by paste/file selection; fully validate it before preview; require human approval for plan, output, status, and activity changes; retain packet and resulting activity event. Optional direct AI uses a replaceable `AIProviderAdapter`; credentials are session memory only, never localStorage, IndexedDB, logs, URLs, analytics, or workspace files. Before sending, show provider, endpoint, model, exact selected content, and purpose, and require confirmation. Network failure leaves workspace unchanged with retryable draft. Do not claim background execution, secure secret storage, WebSockets, or multi-user service behavior.

## 6. Security, compatibility, and recovery

Keep workspace bytes local unless an explicit feature states exactly what will leave the device and receives confirmation. Never upload workspace files for analytics, diagnostics, previews, or crash reporting. Validate manifest, database, packets, worker messages, SQL parameters, imported files, and external responses. Safely render Markdown and imported AI content; never treat it as HTML or executable instructions. Preserve privacy in activity logs and exports. The selected folder boundary, explicit path validation, browser permission checks, and read-only mode are mandatory; these controls do not claim to contain malicious external programs that ignore the protocol.

Use feature detection for File System Access API, Web Locks, BroadcastChannel, Workers, and required WASM support. Explain limitations and offer explicit archive import/download fallback. Reconnection requests permission only from user gestures, detects external changes, preserves active form drafts, and flags conflicts rather than replacing human input. Recover from stale signals, crashed agents, expired leases, committed SQLite changes lacking commit signal, malformed manifests, integrity failures, browser permission loss, worker failures, corrupt database input, future schema, export failure, journal stabilization delay, and watcher restart/cancellation with typed results and concrete user actions. Never overwrite on staleness, conflict, or unexpected fingerprint change.
